## Problem Statement

Agent swarms fail in the same ways that human organizations fail: uncontrolled headcount growth, duplicate effort, institutional amnesia, and invisible waste. Individual agent observability (LangSmith, Braintrust) tells you what an agent did. Orchestration frameworks (LangGraph, CrewAI) tell agents what to do. Nobody tells agents what they're allowed to do, checks if someone else is already doing it, or preserves what they learned when they're done.

AgentHR is the HR department for AI agents. Not a dashboard. Not an observability tool. The actual HR department -- hiring (spawn gates), performance reviews (heartbeats + anomaly detection), promotions (trust progression), exit interviews (exit reports), and institutional knowledge management (searchable memory). The metaphor is structural, not branding.

## Demand Evidence

Honest assessment: demand evidence is thesis-driven, not behavior-driven. The founder has felt the pain of unstructured agent swarms personally but cannot cite a specific dollar cost or specific external user.

Landscape evidence that the problem space is real:
- Multi-agent production failure rates of 41-86.7% (per Galileo AI and Augment Code coordination failure studies, 2026)
- SIDJUA (governance-first agent orchestration) and Omnigent (Databricks, meta-harness for agent governance) both appeared in 2026
- Real practitioners documenting swarm management pain at modest scale (zachwills.net, "8 rules for managing 20 AI agents")
- Agent-swarm.dev publishing governance guides; Arize covering swarm management in harnesses

The key gap: nobody has yet validated that someone will pay for a standalone HR department for agents. The assignment addresses this directly.

## Status Quo

Developers running agent swarms currently manage workforce health by hand: watching logs, checking terminal output, manually killing runaway agents. Observability tools show what happened after the fact. Orchestration frameworks make it easy to spawn agents but provide no backpressure, no duplicate detection, and no institutional memory.

The status quo is "no HR department." Agents are hired (spawned) with no interview process, get no performance reviews, leave with no exit interview, and their knowledge dies when they terminate. The next agent starts from scratch.

## Target User & Narrowest Wedge

Target user: a developer or team lead running 10+ agents using any MCP-compatible system (Claude Code, Cursor, Windsurf, LangGraph, CrewAI, custom systems). They're spending real money on agent compute and discovering failures after the fact.

Narrowest wedge: AgentHR as an MCP server. Any agent system that speaks MCP gets an HR department by adding one MCP server. The agent calls `use_mcp_tool("agenthr", "request_spawn", {...})` and HR runs the hiring process.

## Constraints

- Pre-product, no users, no revenue
- Solo founder
- Existing MVP is well-architected and correctly positioned as a write-path control plane (25 route handlers, 7 tables, anomaly detection, trust progression, exit reports)
- MCP is the dominant agent tool protocol in 2026; broad and growing adoption

## Premises

1. **Agent swarms need an HR department, not just a dashboard.** The write-path (spawn gates, approvals, policy enforcement) IS the value. Read-only monitoring is a byproduct, not the product.
2. **The HR metaphor maps precisely onto real agent lifecycle problems.** Hiring = spawn gates. Performance reviews = heartbeats + anomaly detection. Promotions = trust progression. Exit interviews = exit reports. Institutional knowledge = searchable memory. This is a structural mapping.
3. **AgentHR complements frameworks rather than competing with them.** LangGraph is the office. AgentHR is the HR department. You don't replace the office -- you add HR. The integration: before an agent starts work, it goes through HR.
4. **The HR category is defensible because frameworks are incentivized to make spawning easy, and HR's job is to make spawning thoughtful.** This natural tension prevents absorption. No framework will build a good HR department because their value proposition is frictionless agent execution.

## Approaches Considered

### Approach A: Framework Middleware
`agenthr.wrap(graph)` -- one-line LangGraph integration. Tight coupling, framework-version dependent. Rejected: too narrow, too fragile.

### Approach B: Agent SDK
Explicit `agenthr.checkin()` / `agenthr.heartbeat()` / `agenthr.exit_report()` calls. Framework-agnostic but requires manual integration per agent. Rejected: too much friction, easy to skip.

### Approach C: MCP Server -- CHOSEN
Package AgentHR as an MCP server. Any MCP-compatible agent system gets HR as a tool. Agents interact with HR the way they interact with any tool. Ships in days because the existing API does all the heavy lifting.

## Recommended Approach

**Approach C: MCP Server.** AgentHR becomes an MCP server that any agent can use as a tool.

### MCP Tool Surface

The existing API endpoints back the MCP tools. Not all endpoints are exposed as agent-callable tools -- admin/CRUD operations (get/update/delete individual agent, heartbeat history, degradation checks, violation records, team health, onboarding) remain API-only for human operators. The MCP surface exposes what agents need to interact with HR:

**Hiring (spawn gates):**
- `request_spawn` -- submit a job application. Wraps the existing `POST /agents` (hire_agent) endpoint: HR runs the 4 gates AND creates the agent record in the DB. Returns the agent record with gate results (overlaps found, pressure score, relevant memories). The tool both approves and hires in one step -- like a real HR department that issues the offer letter, not just the approval stamp.
- `list_roster` -- who's currently employed? Active agents by status, team, type, trust level. Backs to `GET /agents`.
- `check_pressure` -- is the organization over-staffed? Current resource pressure score. Backs to `GET /agents/pressure`.

**Performance Reviews (heartbeats):**
- `submit_heartbeat` -- check in with HR. Report what you're doing, what phase you're in, what tools you're using. HR runs anomaly detection and flags issues. Backs to `POST /agents/:id/heartbeat`.
- `get_heartbeat_status` -- how am I doing? Latest anomaly flags. Backs to `GET /agents/:id/heartbeat`.
- `report_stale` -- which employees have stopped checking in? Zombie detection. Backs to `GET /heartbeats/stale`.

**Exit Interviews:**
- `submit_exit_report` -- structured exit interview. What worked, what failed, key findings, recommendations, gaps, dissent. HR updates baselines and trust. Backs to `POST /agents/:id/exit-report`.
- `search_knowledge` -- what did past employees learn? Search the institutional knowledge base. Backs to `GET /exit-reports/search`.

**Trust & Promotions:**
- `check_trust` -- what's the trust level for this agent type? Current evaluation with promotion criteria. Backs to `GET /trust/:type`. Note: trust operates at the agent-type level (not individual agent), matching the existing backend. An analyst agent checks the trust level of the "analyst" type.
- `request_promotion` -- request promotion for an agent type based on collective track record. Backs to `POST /trust/:type/promote`. This promotes the type, not an individual -- matching how the backend works. Individual agent track records contribute to type-level trust.

**Organizational Health:**
- `vital_signs` -- is the organization healthy? Turnover ratio, token efficiency, handoff utilization, memory freshness, output consumption. Backs to `GET /analytics/vital-signs`.
- `hotspots` -- which roles are overloaded? Backs to `GET /analytics/hotspots`.
- `futility_check` -- is anyone doing work that nobody reads? Backs to `GET /analytics/futility`.

**Admin-only (API, not MCP):** Individual agent CRUD (GET/PATCH/DELETE /agents/:id), heartbeat history, baselines, degradation checks, violation records, team health, agent type reports, onboarding. These are for human operators reviewing the workforce, not for agents interacting with HR.

### Implementation Plan

**Phase 1 (Days 1-5): MCP Server Shell**
- Create `agenthr/mcp_server.py` implementing the MCP server protocol using `mcp` PyPI package (modelcontextprotocol/python-sdk, v1.x+)
- Phase 1 scope is the **minimum viable tool subset**: `request_spawn`, `submit_heartbeat`, `submit_exit_report`, `search_knowledge`, `vital_signs`. These 5 tools cover the core HR lifecycle (hire, review, exit, learn, health check). Remaining tools added in Phase 2.
- Map tools to existing service functions. Most tools are thin wrappers; however, some glue logic is needed: `request_spawn` needs to marshal MCP tool input into the `HireRequest` Pydantic model; `submit_heartbeat` needs agent ID lookup from MCP context. No new business logic, but adaptation code is real work.
- Test with Claude Code (add AgentHR as an MCP server in `.claude/settings.json`)
- **Database path in MCP mode:** `~/.agenthr/agenthr.db` (fixed, user-home-relative). Configurable via `AGENTHR_DB_PATH` env var. State is global (shared across projects), not per-project -- the HR department serves the whole organization, not one team.

**Phase 2 (Week 1-2): Dog-food with Claude Code agents**
- Use AgentHR to manage Claude Code subagents on a real project
- Every subagent goes through HR before starting work
- Collect real usage data: how many spawns are blocked? How much duplicate work is prevented? How useful is the institutional knowledge?
- This is both validation and a demo

**Phase 3 (Week 3-4): Polish and distribute**
- Publish via `pip install agenthr` (single Python package, MCP server as CLI subcommand `agenthr mcp-serve`). No separate npm package -- Python-only distribution keeps it simple.
- Add remaining MCP tools (roster, pressure, heartbeat status, stale, trust, promotion, hotspots, futility)
- Documentation: "Add HR to your agent system in 5 minutes"
- Open source with real dog-food data showing HR's value

## Open Questions

1. **MCP transport:** stdio (local) or SSE (remote)? stdio is simplest for local dev. SSE enables hosted AgentHR-as-a-service. Likely ship stdio first, SSE in Phase 3.
2. **Dog-food scope:** What project should you use to dog-food AgentHR managing Claude Code subagents? Ideally something with 5-10 subagents working in parallel.
3. **The "easy to skip" problem:** Unlike middleware, MCP tools are opt-in. An agent can choose not to go through HR. For v1, this is accepted as a feature (flexibility) rather than treated as a bug. Enforcement mechanisms exist but are deferred: (a) system-prompt instructions that tell agents "always go through HR before spawning," (b) wrapper agents that gate tool access, (c) framework-level hooks that intercept spawn calls. The dog-food phase will test whether system-prompt-level enforcement ("you MUST call request_spawn before starting work") is sufficient in practice. This tension with Premise 1 ("the write-path IS the value") is acknowledged: if agents routinely bypass HR, the product thesis weakens. Dog-food data will determine whether stronger enforcement is needed.

## Success Criteria

1. Dog-food AgentHR managing 5+ Claude Code subagents on a real project. HR blocks at least one bad spawn and surfaces at least one piece of useful institutional knowledge.
2. One external developer adds AgentHR as an MCP server and says "I didn't know my agents were duplicating work."
3. Institutional knowledge from exit reports is demonstrably useful to subsequent agents (an agent references a predecessor's findings and avoids a known dead end).

## Distribution Plan

Single Python package: `pip install agenthr`. MCP server exposed as CLI subcommand: `agenthr mcp-serve`.

Users add AgentHR to their MCP config:
```json
{
  "mcpServers": {
    "agenthr": {
      "command": "agenthr",
      "args": ["mcp-serve"]
    }
  }
}
```
CI/CD: GitHub Actions for PyPI publish on tag. No npm package -- Python-only keeps distribution simple and matches the existing codebase.

## Dependencies

- MCP SDK: `mcp` PyPI package (modelcontextprotocol/python-sdk, v1.x+). This is the official Python SDK for the Model Context Protocol.
- Existing AgentHR codebase (core business logic unchanged; MCP server adds adaptation/marshalling layer)
- A real project to dog-food with (Phase 2)

**Overlap detection limitation (inherited from existing codebase):** The spawn gate's overlap detection uses keyword tokenization with Jaccard similarity (0.3 threshold). This will miss semantically similar mandates with different vocabulary ("refactor the auth module" vs. "rewrite the login system"). For v1 dog-food, this is acceptable -- keyword overlap catches the obvious duplicates. If false-negative rates undermine the dog-food success criterion ("HR blocks at least one bad spawn"), embedding-based similarity is the upgrade path.
